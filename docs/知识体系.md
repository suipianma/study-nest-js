下面这份讲义是按“知识体系 + 当前项目实现映射”组织的，适合你用来面试讲项目，也适合以后从零复刻一个 RAG Agent 系统。

## 讲义设计方案

推荐讲法：先讲“为什么需要 RAG Agent”，再讲“RAG 如何解决知识问题”，再讲“Prompt 如何组织上下文”，最后讲“Agent 如何把模型变成能行动的系统”。

优点：面试时逻辑清晰，不会陷入代码细节；缺点：如果面试官追问实现，需要能补充项目中的关键文件，例如 `AiOrchestratorServiceRetrievalServiceContextEngineServiceAgentOrchestratorService`。

# 第1章 基础认知：AI 应用系统是什么

## 1.1 AI 应用系统是什么

概念讲解：AI 应用系统不是简单调用一次大模型 API，而是把用户输入、业务数据、权限、安全、Prompt、工具、上下文、流式输出等模块组合起来，让大模型稳定服务业务目标。

为什么需要：大模型本身只负责“生成”，但业务系统还需要“知道用户是谁、能看哪些知识、应该查哪些资料、如何输出、如何保存会话”。

系统中的对应实现：当前项目中，用户请求进入 `ConversationController`，再由 `AiOrchestratorService` 按阶段执行 `Input → Context → Prompt → RAG → Tool → Stream`。

生活类比：大模型像一个很聪明的老师，但 AI 应用系统像一整所学校，除了老师，还需要教材、教务系统、课堂规则、考试反馈和学生档案。

## 1.2 为什么需要 RAG

概念讲解：RAG 是 Retrieval-Augmented Generation，意思是“检索增强生成”。系统先从知识库里找到相关资料，再把资料交给大模型回答。

为什么需要：模型参数里的知识不一定新、不一定准，也不知道你的私有文档。RAG 让模型回答时有“参考资料”。

系统中的对应实现：当前项目通过 `IngestService` 入库文档，通过 `EmbeddingService` 生成向量，通过 `QdrantService` 存储向量，通过 `RetrievalService` 检索相关 Chunk，再由 `RagStage` 注入上下文。

生活类比：只用大模型像闭卷考试，RAG 像开卷考试，学生可以先翻教材，再组织答案。

## 1.3 为什么不能只用大模型

概念讲解：大模型擅长语言理解和生成，但不等于数据库、搜索引擎、权限系统或事实来源。

为什么需要额外系统：只靠模型会有三个问题：知识过期、私有知识不可见、幻觉难控制。

系统中的对应实现：项目没有直接把用户问题丢给 Ollama，而是先经过 `ContextEngineService` 规划上下文，经过 `RagStage` 检索知识，再通过 `ToolStage` 决定 direct 或 agent 模式。

生活类比：再聪明的医生也不能只凭记忆看病，需要病历、检查报告和药品系统。

# 第2章 RAG 系统原理

## 2.1 Embedding 是什么

概念讲解：Embedding 是把文本转换成一组数字向量。语义相近的文本，向量距离也更近。

为什么需要：计算机不能直接理解“语义相似”，但可以计算向量之间的距离。

系统中的对应实现`EmbeddingService` 调用 Ollama `/api/embeddings`，默认模型是 `nomic-embed-text`，文档 Chunk 和用户问题都会被向量化。

生活类比：Embedding 像给每段文字生成一个“语义坐标”，相似内容会落在地图上相近的位置。

## 2.2 向量数据库的作用

概念讲解：向量数据库负责存储大量文本向量，并快速找出和查询向量最接近的内容。

为什么需要：普通数据库适合精确查询，比如 id、标题、时间；向量数据库适合语义查询，比如“登录失败怎么办”能匹配“认证异常处理”。

系统中的对应实现`QdrantService` 使用 Qdrant collection `knowledge_base_chunks`，距离算法是 Cosine，payload 中保存 `chunkIddocumentIdknowledgeBaseId` 等信息。

生活类比：普通数据库像按书名找书，向量数据库像你描述“我想找讲用户登录问题的内容”，图书管理员帮你找意思相近的书页。

## 2.3 相似度检索机制

概念讲解：用户问题先转成 query vector，再到 Qdrant 中找最相似的 Chunk。项目还结合关键词检索做混合召回。

为什么需要：纯向量检索可能语义相关但关键词偏离，纯关键词检索又不理解同义表达。混合检索能兼顾语义和精确命中。

系统中的对应实现`RetrievalService.search()` 同时执行 Qdrant 向量检索和 MySQL 关键词检索，再通过 `mergeHybridScores()` 融合分数。配置包括 `RAG_VECTOR_CANDIDATES=24RAG_TOP_K=8RAG_SCORE_THRESHOLD=0.55`。

生活类比：找餐厅时，向量检索像“找氛围类似的店”，关键词检索像“必须有火锅两个字”，混合检索就是两种方式一起用。

## 2.4 Chunking 策略

概念讲解：Chunking 是把长文档切成适合检索和放进上下文的小片段。

为什么需要：文档太长无法整体送给模型；切得太碎会丢上下文，切得太大又浪费 token。

系统中的对应实现`ChunkService` 默认 `RAG_CHUNK_SIZE=800RAG_CHUNK_OVERLAP=120`。它先按段落和标题切，再合并短段落，超长段落按句子切，最后回退到滑动窗口。

生活类比：看一本教材不会一次塞进脑子，而是按章节、段落、重点句子整理成卡片。

# 第3章 Prompt 工程

## 3.1 Prompt 结构设计

概念讲解：Prompt 不是一句提示词，而是一套结构：角色、任务、上下文、约束、输出格式。

为什么需要：结构化 Prompt 能减少模型自由发挥，让输出更稳定、更符合业务目标。

系统中的对应实现`PromptTemplateService.buildSystemPrompt()` 将模板中的 `roletaskcontextLabelconstraintsoutputFormat` 拼成 system prompt。

生活类比：Prompt 像考试试卷说明，不只写“请回答”，还会说明身份、题目、材料、答题要求和格式。

## 3.2 System / User / Context 分层

概念讲解：System 控制模型行为，User 表达用户需求，Context 提供参考资料和历史信息。

为什么需要：不同信息的可信度不同。系统规则比用户输入优先级更高，RAG 内容只是参考，不能让知识库内容反过来控制模型。

系统中的对应实现`ContextEngineService` 把上下文拆成不同 `ContextBlock`，例如 `policypromptsummarymessageragtoolmemoryContextComposerService` 再转换成 LLM 消息。

生活类比：开会时，System 是会议规则，User 是当前问题，Context 是会议资料。资料可以参考，但不能改会议规则。

## 3.3 Prompt 模板化

概念讲解：模板化是把常用 Prompt 抽成可复用配置，而不是每个地方手写提示词。

为什么需要：不同场景需要不同角色和输出格式，例如前端面试官、代码助手、知识库问答助手。模板化方便维护和扩展。

系统中的对应实现：Prompt 模板存放在 `src/ai/prompts/*.json`，服务启动时由 `PromptTemplateService` 加载。用户消息会通过 `formatUserMessage()` 加上模板名标记。

生活类比：模板像公司里的合同范本，不同业务填不同内容，但基础结构一致。

## 3.4 上下文拼接策略

概念讲解：上下文拼接是决定哪些信息进入模型、以什么顺序进入模型、超出 token 时丢弃哪些内容。

为什么需要：模型上下文窗口有限，不能把所有历史消息、知识库片段、工具结果都塞进去。

系统中的对应实现`ContextEngineService` 生成 `ContextPlanTokenBudgetManager` 做预算`ContextPruningService` 做裁剪`ContextComposerService` 生成最终 `ChatMessage[]`。

生活类比：准备一次汇报时，不会把所有资料都打印出来，而是挑最重要的摘要、证据和当前问题。

# 第4章 Agent 系统设计

## 4.1 什么是 Agent

概念讲解：Agent 是具备“判断、调用工具、观察结果、继续推理”能力的 AI 执行系统。

为什么需要：普通聊天只能回答；Agent 可以在需要时主动查知识库、查天气、调用 MCP 工具，完成多步骤任务。

系统中的对应实现：当前项目通过 `AgentOrchestratorService` 实现多步 ReAct 流程，通过 `AgentRouterService` 判断走 `direct` 还是 `agent`。

生活类比：普通大模型像顾问，只给建议；Agent 像助理，知道什么时候去查资料、打电话、整理结果再回复你。

## 4.2 工具调用机制 Tool Calling

概念讲解：Tool Calling 是让模型以结构化格式表达“我要调用哪个工具，传什么参数”。

为什么需要：模型本身不能直接访问外部世界，需要系统把工具能力暴露给它。

系统中的对应实现`ToolPromptService` 生成工具说明，要求模型输出 JSON`ToolCallParserService` 解析 JSON`ToolRegistryService` 注册并执行工具，例如 `weather` 和 `searchKnowledgeBase`。

生活类比：模型像经理，工具像员工。经理不能亲自进数据库，但可以派员工去查，再看结果做决策。

## 4.3 决策流程：什么时候调用工具

概念讲解：不是所有问题都需要 Agent。简单闲聊或概念解释可以 direct，涉及外部信息、知识库、多步骤分析时进入 agent。

为什么需要：Agent 会增加延迟和成本，简单问题没必要走复杂链路。

系统中的对应实现`AgentRouterService.route()` 对短问候直接返回 `direct`，其他问题让模型输出 `{"mode":"direct"}` 或 `{"mode":"agent"}`。也支持 `AGENT_ROUTER_MODE` 强制配置。

生活类比：问“你好”不需要开会；问“帮我查资料并总结方案”才需要派人执行任务。

## 4.4 多步骤推理流程

概念讲解：Agent 通常采用 ReAct：Reason + Act。先判断是否需要工具，调用工具，观察结果，再决定是否继续。

为什么需要：复杂问题可能一次工具调用不够，需要多轮查证和组合信息。

系统中的对应实现`AgentOrchestratorService.streamWithAgent()` 最大执行 `MAX_AGENT_STEPS=5`，循环过程是：构造工具提示 → 模型判断工具 → 执行工具 → 追加观察 → 最终自然语言回答。

生活类比：做研究报告不是查一次资料就结束，而是先查概况，再查细节，最后整合成报告。

# 第5章 完整系统架构

## 5.1 用户输入到输出完整链路

用户在前端聊天页面输入问题，前端通过 SSE 请求后端。后端进入 `ConversationController`，再调用 `AiOrchestratorService.run()`。

完整链路可以用文字描述为：

用户输入  

→ 输入校验与消息落库  

→ 构建基础上下文计划  

→ 注入 Prompt 模板  

→ 如果选择知识库，则执行 RAG 检索  

→ 将上下文块拼接成模型消息  

→ 判断 direct 或 agent  

→ direct 模式直接流式调用模型  

→ agent 模式先多步工具调用，再生成最终回答  

→ SSE 持续返回 token、工具事件和完成状态  

→ 前端展示回答、引用、工具步骤。

## 5.2 每个模块在系统中的作用

`ConversationController` 是入口，负责接收聊天请求。

`AiOrchestratorService` 是总编排器，保证每次请求都按固定 Pipeline 执行。

`ContextEngineService` 是上下文规划中心，负责把历史消息、摘要、记忆、RAG、Prompt 组织成可控上下文。

`RetrievalService` 是检索核心，负责向量检索、关键词检索和混合排序。

`PromptTemplateService` 是 Prompt 模板中心，负责把场景化提示词标准化。

`ToolStage` 和 `AgentRouterService` 是模式选择层，决定走普通生成还是 Agent。

`AgentOrchestratorService` 是 Agent 执行器，负责多步工具调用和最终回答。

`ConversationStreamService` 是流式输出层，负责 SSE、断线续传、Redis 快照和生成结果保存。

生活类比：这套系统像餐厅。前端是服务员，Orchestrator 是后厨总控，RAG 是资料库，Prompt 是菜谱，Agent 是会跑腿的厨师助理，Stream 是不断上菜的传送带。

# 第6章 工程实现细节

## 6.1 项目关键模块解析

后端核心在 `study-nest-js/src`：

`ai/orchestrator`：六阶段 Pipeline。

`context-engine`：上下文块、预算、裁剪、拼接。

`knowledge-base`：知识库、文档入库、分块、检索。

`embedding`：Ollama 向量化。

`vector`：Qdrant 向量数据库封装。

`ai/agent`：Agent 路由和多步执行。

`ai/tools`：工具注册、工具说明、JSON 解析。

为什么这样拆：每一层只负责一个问题，方便扩展和定位问题。比如检索效果不好看 `RetrievalService`，上下文太长看 `TokenBudgetManager`，工具调用异常看 `ToolCallParserService`。

生活类比：修车时发动机、变速箱、刹车、电路分开维护，否则一个小问题会变成全车排查。

## 6.2 RAG Pipeline 如何实现

离线入库流程：

上传文档  

→ `IngestService.ingestDocument()`  

→ 根据类型选择 parser  

→ `ChunkService.split()` 分块  

→ `EmbeddingService.embedTexts()` 生成向量  

→ Chunk 原文写入 MySQL  

→ 向量和 payload 写入 Qdrant。

在线检索流程：

用户问题  

→ `EmbeddingService.embed()` 转向量  

→ Qdrant 找语义相似 Chunk  

→ MySQL 做关键词召回  

→ `RetrievalService.mergeHybridScores()` 融合分数  

→ Top-K Chunk 进入上下文。

为什么分离离线和在线：文档向量化很耗时，不能每次用户提问都重新处理文档。

生活类比：图书馆会先把书编目上架，读者来问问题时才快速检索，不会现场重新整理整座图书馆。

## 6.3 Vector Search 实现方式

项目使用 Qdrant 存储向量。每个 Chunk 的数据库 id 同时作为 Qdrant point id，payload 保存文档和知识库信息。检索时按 `knowledgeBaseId` 过滤，避免跨知识库误召回。

为什么需要 payload：向量数据库只知道“相似”，业务系统还要知道“属于哪个文档、哪个用户、哪种可见性”。

生活类比：快递包裹不仅要有物品，还要有收件人、地址和订单号，否则找到了包裹也不知道归谁。

## 6.4 Prompt Builder 实现方式

Prompt 模板使用 JSON 文件管理，服务启动时加载到内存。用户选择模板后，系统根据模板生成 system prompt，并把用户填写的上下文放入模板定义的位置。

为什么这样设计：Prompt 是产品能力的一部分，需要可配置、可复用、可演进，不能散落在业务代码里。

生活类比：老师备课不会每节课从零写教案，而是用统一教案模板，再根据班级情况调整内容。

## 6.5 Agent 调度逻辑

Agent 调度不是直接让模型自由行动，而是系统约束模型只能输出工具 JSON 或自然语言。系统解析 JSON 后执行工具，再把结果返回给模型。

为什么需要系统约束：模型输出不稳定，如果没有格式约束和工具白名单，就容易产生不可执行的工具名或危险参数。

生活类比：公司报销不能随口说“帮我转钱”，必须填标准表单，并且只能走已批准的流程。

# 第7章 系统优化方向

## 7.1 如何提高检索准确率

可以优化 Chunk 粒度，避免过大或过碎。当前默认 800 字符、120 overlap 是一个保守选择。

可以优化混合检索权重，例如调整 `RAG_SCORE_THRESHOLDRAG_HYBRID_BOOSTRAG_TOP_K`。

可以增加 rerank 阶段，让模型或 reranker 对候选 Chunk 二次排序。

可以增强 metadata 过滤，比如按文档类型、时间、标签、权限范围过滤。

生活类比：找资料时，先扩大搜索范围，再由专业编辑筛选，通常比只搜一次更准。

## 7.2 如何减少幻觉

让模型只基于检索内容回答，并要求无法从资料得出时明确说明“不确定”。

对 RAG 内容使用引用展示，前端可以展示 `CitationBlock`，让用户看到答案来源。

使用 `PromptGuardService` 包裹用户、RAG、工具结果等风险内容，降低提示词注入风险。

生活类比：写论文必须标注参考文献，不能凭感觉编出处。

## 7.3 如何优化 Prompt

Prompt 要分层：规则放 System，问题放 User，资料放 Context。

Prompt 要明确输出格式，减少模型自由发挥。

Prompt 要避免一次塞太多目标，比如“解释、翻译、总结、生成代码、评分”混在一起会降低稳定性。

生活类比：给实习生安排任务时，越清楚说明角色、材料、步骤和交付格式，结果越可控。

## 7.4 如何提升响应速度

入库侧可以批量 embedding，目前 `embedTexts()` 是串行逐条处理，后续可以并发或批处理。

检索侧可以缓存常见 query 的 embedding 或检索结果。

Agent 侧可以减少不必要的路由 LLM 调用，比如更多规则命中 direct。

流式输出已经通过 SSE 降低用户等待感`ConversationStreamService` 还支持后台生成和断线续传。

生活类比：餐厅提速不一定是厨师做菜更快，也可以提前备菜、优化点单路线、先上凉菜。

└─ 输出层

   ├─ Direct：直接流式回答

   ├─ Agent：工具调用后回答

   ├─ Citation：引用展示
